## Plan 04-01 Task 3 — PAR-07 NPS scaling sentinel

**Status:** DEFERRED on the Windows dev host.
**Blocking:** Plan 04-02 PAR-09 gauntlet (must confirm Lazy SMP actually scales before
measuring Elo gain — if 4t/1t ratio < 3.0, diagnose Pitfall 1 before gauntlet run).

### Why this is deferred

The PAR-07 NPS-scaling sentinel requires:
1. A compiled `v7_engine.pyd` native module (needs CMake + C++17 toolchain).
2. A quiet single-CPU host where background load doesn't skew the 4t/1t ratio
   comparison (noisy measurement environment → spurious pass or fail).

Both conditions are absent on the Windows dev host (MSVC unavailable; background
load is variable). Per PATTERNS.md Shared Pattern 5 and the Phase 1/3 precedent,
runtime benchmark gates ship as plumbing on the dev host and run on the build host.

Plan 04-01 Tasks 1 (test scaffolding — commit `8fc356f`) and 2 (ThreadPool + Worker
implementation — commit `e06865e`) ARE complete on the dev host.

### Reproduction

On a build host with CMake + C++17 toolchain + `uv`:

```bash
# From repo root:
git pull origin main
python3 -m uv run --group dev python -c "from chess_engine.engine.v7 import chess_algorithm as v7; v7.ensure_available(auto_build=True)"
RUN_BENCHMARKS=1 python3 -m uv run --group dev pytest tests/test_v7_lazy_smp.py::test_nps_scales_3x_4t_vs_1t -q
```

### Pass criterion

Test exits 0 and prints output containing:

```
PAR-07: nps_1=<N> nps_4=<M> ratio=<R>
```

where `ratio >= 3.0`. The exact measured values should be recorded in the Result
subsection below after running on the build host.

### Fail behavior

Test fails with:

```
AssertionError: 4t/1t NPS ratio <R> < 3.0 threshold
```

If the ratio is < 1.5×: most likely cause is Pitfall 1 (worker tables sharing via
reference — value-typed copies aliasing). Check that Worker struct fields
`history`, `counter_moves`, `continuation_history`, `capture_history` are NOT
references to Engine members (they must be zero-initialized arrays inside Worker).

If the ratio is 1.5×–3.0×: GIL contention (FOUND-05). Verify `python_bindings.cpp`
`m.def("search")` has `py::call_guard<py::gil_scoped_release>()`. Also check that
helper threads do not touch Python objects (thread_pool.cpp touches no py:: APIs).

Do NOT proceed to Plan 04-02 PAR-09 gauntlet until this test passes.

## Plan 04-01 Task 3 — PAR-08 cancellation latency sentinel

**Status:** DEFERRED on the Windows dev host.
**Blocking:** Plan 04-02 PAR-09 gauntlet (cancellation must be < 50ms before
multi-game gauntlet — ensures the engine can be reliably stopped between moves).

### Why this is deferred

Same reasons as PAR-07: needs a compiled `v7_engine.pyd` and a build host.
Additionally, the 50ms cancellation threshold requires that OS thread scheduling
is not too loaded (high system load can inflate the poll cycle's wall clock).

### Reproduction

On a build host:

```bash
# From repo root (v7_engine must already be built — see PAR-07 Reproduction):
RUN_BENCHMARKS=1 python3 -m uv run --group dev pytest tests/test_v7_lazy_smp.py::test_cancellation_under_4_threads_under_50ms -q
```

### Pass criterion

Test exits 0 and prints output containing:

```
PAR-08: elapsed_ms=<E>
```

where `elapsed_ms < 50.0`. The exact measured value should be recorded in the
Result subsection below.

### Fail behavior

Test fails with:

```
AssertionError: cancellation took <E>ms (threshold 50ms)
```

If elapsed_ms > 50ms: most likely cause is Pitfall 10 (cancellation poll cadence
too coarse). Verify `search.cpp` has `% 1024` (not `% 4096`) at BOTH poll sites
(qsearch line ~79, alpha_beta line ~174). The grep check:

```bash
grep -c "% 1024" src/chess_engine/engine/v7/src/search.cpp   # must return >= 2
grep -c "% 4096" src/chess_engine/engine/v7/src/search.cpp   # must return 0
```

Also verify that `stop()` called from Python (which holds the GIL) correctly
propagates through `shared_stop` atomic to all worker threads.
