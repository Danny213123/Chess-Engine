<interfaces>
KPK bitbase reference encoding (RESEARCH.md Pitfall 5 — Stockfish-style):
  index = stm | (bksq << 1) | (wksq << 7) | (psq << 13)
  Symmetry fold: pawn always white; black-to-move folds into white-to-move by swapping piece colors; white king mirrored to files a-d to halve the table (yielding 163,328 unique entries from 64*64*48*2 = 393,216 raw tuples).
  Generator script must:
    1. Enumerate all (wksq, bksq, psq, stm) tuples satisfying:
       - wksq != bksq && wksq != psq && bksq != psq (no overlap)
       - psq on ranks 2..7 (white pawn cannot be on rank 1 or 8 here — promoted positions handled separately)
       - kings not adjacent (illegal)
       - if stm == BLACK, white king not in check from BLACK (not the side to move's king)
       - if stm == WHITE, black king not in check from WHITE
    2. BFS-classify each as WIN-for-WTM-or-DRAW using canonical retrograde analysis (mate-in-N then unwind)
    3. Cross-check 100% against Fathom's tb_probe_wdl (KPK is 3-men, always in tablebase range) — abort generation on any mismatch
    4. Pack into uint8_t[20416] via numpy.packbits and emit kpk_bitbase.cpp
    5. Output is byte-deterministic across reruns and across machines (D-13 contract from coeffs codegen — mirror)

  Runtime probe (endgame.cpp):
    bool kpk_is_win(Color stm, Square wksq, Square bksq, Square psq) {
        // Normalize: if pawn is on left half, mirror everything
        // Apply Stockfish-style index formula above
        int idx = kpk_index(stm, wksq, bksq, psq);
        return (KPK_BITBASE[idx >> 3] >> (idx & 7)) & 1;
    }

  CONTEXT D-10 acceptance: pytest test verifies kpk_is_win matches Fathom across all 163,328 positions. The generator already cross-checks at write time; this test verifies the runtime probe (which independently re-derives the index) matches.

Opposition eval (ENDG-02, RESEARCH.md D3 §4.2):
  Definition: in a K-vs-K-vs-P ending (and analogous), "opposition" means the kings are on the same file/rank/diagonal with an odd number of squares between them AND it is the OTHER side's turn to move. Direct opposition (1 square apart on the same rank/file) is the most common case.
  Implementation: helper `bool has_opposition(Board const&, Color side_with_opposition)`. Bonus value = `v7::coeffs::opposition_value` (added to coeffs.json per D-12) applied with the correct sign (positive for the side with opposition).

Wrong-bishop + rook-pawn (ENDG-03, RESEARCH.md D3 §4.3):
  Detection: side has K + B + RP (only the a-pawn or h-pawn, no other pawns/pieces); the bishop is the WRONG color for the promotion square (a-pawn promotes on a8 (light square): wrong bishop is dark-squared; h-pawn promotes on h8 (dark square): wrong bishop is light-squared); the defending king can reach the promotion square (king-distance ≤ pawn-distance + 1 — canonical check).
  Action: scale the score toward DRAW. Implementation hint: return `DRAW_SCORE` (0) from endgame_eval when the position matches, OR multiply the existing eval by 0 (or a small scale like `v7::coeffs::wrong_bishop_rp_scale` defaulting to 0 — keeps the term tunable).

Phase blend formula (ENDG-04, RESEARCH.md Pitfall 6):
  Replaces V7 eval.cpp:425 `int final_score = (mg * phase + eg * (24 - phase)) / 24;` with:
    int npm = std::clamp(non_pawn_material(WHITE) + non_pawn_material(BLACK),
                         v7::coeffs::endgame_limit, v7::coeffs::midgame_limit);
    int phase = ((npm - v7::coeffs::endgame_limit) * 256) /
                (v7::coeffs::midgame_limit - v7::coeffs::endgame_limit);

  endgame_limit and midgame_limit are NEW coeffs (D-12). Initial canonical values: endgame_limit = 0 (or thereabouts — bare kings), midgame_limit = sum of all non-pawn piece values for both sides at the starting position (≈ 6196 using canonical 325/325/500/975 values × 2 of each).
  Replaces also the phase accumulator at eval.cpp:158-160 (which currently uses popcount × phase_weight). The new path computes phase from non_pawn_material(WHITE) + non_pawn_material(BLACK) — reusing the helper added in Plan 03-02 Task 1.
